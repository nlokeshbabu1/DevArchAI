# Database Migrations

This project uses **Alembic** (v1.14+) for database schema migrations. All schema changes must be done through versioned migration scripts — no manual SQL or `Base.metadata.create_all()`.

## Architecture

- **Driver split**: Async (`asyncpg`) at runtime, sync (`psycopg2`) for Alembic
- **Migration location**: `backend/app/db/migrations/versions/`
- **Auto-detection**: Alembic `env.py` imports `app.models` to reflect `Base.metadata`
- **Startup**: `app/db/migrate.run_migrations()` runs `alembic upgrade head` at every startup

## Commands

All commands run from `backend/`.

| Action | Command |
|--------|---------|
| Generate new migration | `alembic revision --autogenerate -m "description"` |
| Apply pending migrations | `alembic upgrade head` |
| Rollback one step | `alembic downgrade -1` |
| Rollback to a specific revision | `alembic downgrade <revision_id>` |
| Show current revision | `alembic current` |
| Show migration history | `alembic history` |
| Check for pending migrations | `alembic check` |
| Show SQL (dry run) | `alembic upgrade head --sql` |

## Workflow

### 1. Create a new migration

```bash
cd backend
source .venv/bin/activate

# After changing a model in app/models/
alembic revision --autogenerate -m "add_foobar_to_users"
```

Review the generated file in `app/db/migrations/versions/`, then:

```bash
alembic upgrade head
```

### 2. Migration best practices

- **Always review** autogenerated migrations — they may miss edge cases
- **Set `nullable=True`** for new columns on existing tables (prevents errors on populated DBs)
- **Provide server defaults** for non-nullable new columns
- **Test reversibility**: verify `alembic downgrade -1` works cleanly
- **No data loss**: never create a migration that drops or truncates data without explicit approval

### 3. CI/CD integration

In CI (GitHub Actions), migrations run automatically:

```yaml
- name: Run database migrations
  run: |
    cd backend
    alembic upgrade head
```

The Docker entrypoint (`docker-entrypoint.sh`) also runs `alembic upgrade head` before starting the application.

## Transition from `create_all()`

Previously, `init_db()` called `Base.metadata.create_all()`. The migration runner now detects this situation:

1. If `alembic_version` table is missing but app tables exist → stamps head automatically
2. If no tables exist → runs all migrations from scratch
3. If `alembic_version` exists → runs any pending migrations

## Troubleshooting

### "Target database is not up to date"

```bash
alembic upgrade head
```

### Migration fails with "relation already exists"

The database was likely created by `create_all()`. Try:

```bash
alembic stamp head
alembic upgrade head
```

### Detached from head after branch

```bash
alembic merge heads
```
